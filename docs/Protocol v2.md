# Mudi 外屏插件系统 — Protocol v2

> **地位：本文档是 Core 与插件之间的唯一契约。**
> 任何一侧的实现与本协议冲突时，以本文档为准。
> 版本：v2（`MUDI_API_VER = 2`） · 状态：已冻结，向后兼容演进

---

## 1. 设计原则

1. **插件零 UI**。插件不接触 LVGL、fb0、触摸设备，只声明"我有什么状态、什么动作"。
2. **Core 是唯一渲染者**。页面结构、布局、颜色、字体、导航全部由 Core 的页面模板决定。插件无法决定像素，也无法把界面搞乱。
3. **声明式对象模型**。协议不传输绘制指令，只传输对象（switch/info/menu/list/item）及其属性。新对象类型可新增（slider/badge/…），协议骨架不变。
4. **文本线协议**。开发期人类可读、`echo` 可调试；字段结构已按 `k=v` 设计，未来可平滑升级为 length-prefixed JSON 而不改骨架。

## 2. 传输层

- **通道**：插件进程的 `stdin`（Core→插件）与 `stdout`（插件→Core），由 Core `fork+exec` 时建立管道。
- **格式**：每行一条消息；字段以 **TAB（`\t`）** 分隔；行以 `\n` 结束。
- **约束**：
  - 任何字段值内 **不得包含 `\t` 或 `\n`**。
  - 单行最大 **2048 字节**（含 `\n`）。
  - 插件每发完一行必须 `fflush(stdout)`（libplugin 已内置）。
  - **插件的 stdout 是协议专用通道**：调试日志只能写 `stderr` 或文件，写 stdout 即协议损坏。
- **进程纪律**：双端都必须 `signal(SIGPIPE, SIG_IGN)`。插件死亡后 Core 写管道会触发 SIGPIPE，不忽略则 Core 被杀、屏幕冻结（真实事故）。

## 3. 生命周期与握手

```
Core 启动会话(用户滑入)
  └─ fork+exec 每个可见插件
       ├─ 插件首行必须发:  HELLO → 见 §4.1
       └─ Core 随后发:     INIT  → 插件推入口卡片数据
用户打开插件详情页  → Core 发 OPEN  → 插件声明页面对象(OBJ...)
用户交互          → Core 发 EV    → 插件执行并用 SET/BUSY 更新
用户离开详情页    → Core 发 CLOSE → Core 销毁该插件全部页面对象
每秒              → Core 发 TICK  → 插件做轮询/状态同步
会话结束(退出/锁屏) → Core 发 EXIT → 插件自行退出
```

**CLOSE 语义（重要）**：Core 在 CLOSE 后销毁插件的全部详情页对象与列表内容。
因此 **`on_open` 必须幂等地完整重新声明**所有页面对象；不能假设上次声明还在。

## 4. 消息定义 — 插件 → Core

### 4.1 `HELLO` — 握手（必须第一行）

```
HELLO\t<api_ver>\t<name>
```

- `api_ver`：整数，当前为 `2`。Core 据此做兼容判断。
- `name`：插件显示名，用于卡片标题与详情页标题栏（可覆盖 manifest 的 name）。

### 4.2 `CARD` — 入口卡片状态徽章

```
CARD\tON        CARD\tOFF
```

主菜单卡片右上角的 ON/OFF 徽章。插件应在状态变化时实时推送。

### 4.3 `CF` — 入口卡片内容行

```
CF\t<row>\t<text>\t<color>
```

| row | 位置 |
|---|---|
| `r2` | 卡片第 2 行（如 `Rule · hneko`） |
| `r3l` | 卡片第 3 行左（如 `节点名 · 23ms`） |
| `r3r` | 卡片第 3 行右（如 `YT 120 · GH 88`） |

`color` 见 §6 颜色词表。OFF 态建议只推 `r2=已停止`，其余置空。

### 4.4 `OBJ` — 声明页面对象（在 on_open 中）

```
OBJ\tswitch\t<id>\tlabel=<文本>\tvalue=<0|1>
OBJ\tinfo\t<id>\tlabel=<文本>\tvalue=<文本>\tcolor=<颜色>
OBJ\tmenu\t<id>\tlabel=<文本>\tvalue=<文本>
OBJ\tlist\t<id>\ttitle=<列表页标题>\tbtn=<头部按钮文本或空>
OBJ\titem\t<list_id>/<iid>\tlabel=<文本>\tsub=<右侧值>\tcolor=<颜色>\tsel=<0|1>
```

对象类型与渲染：

| type | 渲染 | 交互 |
|---|---|---|
| `switch` | 标签 + 右侧开关 | 拨动 → `EV <id> 0|1` |
| `info` | 左标签 + 右值（值按 color 变色） | 只读 |
| `menu` | 左标签 + 右当前值 + `›` | 点击：若存在同 id 的 `list` → 打开列表页；否则 → `EV <id> tap` |
| `list` | 不可见声明，定义一个单选列表页 | 由同 id menu 行进入 |
| `item` | 列表行：左 label（选中带 ✓ + 行高亮）+ 右 sub（按 color 变色） | 点击 → `EV <list_id> <iid>`，Core 自动返回详情页 |

**规则**：
- `id` 在插件内唯一，`[a-zA-Z0-9_-]`，建议短（`svc`/`run`/`mode`/`nodes`）。
- `menu` 与 `list` **同 id 即绑定**：声明 `menu("nodes",…)` + `list("nodes",…)` 后，点菜单行自动进入节点列表页，插件不收到 tap 事件。
- `item` 的完整 id 为 `<list_id>/<iid>`；`iid` 允许包含空格与 `/`（按第一个 `/` 切分）。
- `list` 的 `btn` 非空时，列表页标题栏右侧出现按钮，点击 → `EV <list_id> @btn`（如"测速"）。
- 上限：`MAX_LISTS=4` 个列表/插件，`MAX_ITEMS=64` 项/列表，`MAX_PLUGINS=8` 插件/系统。

### 4.5 `SET` — 运行期更新对象

```
SET\t<id>\tvalue=<文本>\tcolor=<颜色>
SET\t<id>\tchecked=<0|1>
SET\t<list_id>/<iid>\tvalue=<文本>\tcolor=<颜色>     # 更新列表项 sub
SET\t<list_id>/<iid>\tchecked=<0|1>                  # 更新列表项选中态
```

- 详情对象：`value`+`color` 更新右值；`checked` 更新开关（不触发 EV 回环）。
- 列表项：`value` 更新 sub（如延迟数值与变色），`checked` 移动 ✓。
- 更新立即反映到已渲染的 UI；页面未打开时仅更新数据，打开时生效。

### 4.6 `LEND` — 列表批量渲染

```
LEND\t<list_id>
```

一批 `item` 发送完毕后调用，Core 一次性重绘该列表页。
**必须遵守**：逐项渲染是 O(n²)，54 个节点实测卡顿；先发完 item 再 LEND。
`OBJ list` 会清空该列表全部 item，重载流程 = `OBJ list` → n×`OBJ item` → `LEND`。

### 4.7 `BUSY` — 阻塞遮罩

```
BUSY\t1       # 全屏 50% 黑 + spinner + "处理中…"，吞掉一切触摸/手势/按钮
BUSY\t0       # 解除
```

用于**需要等待返回结果的长操作**（服务启停、重启、切换配置、测速）。
Core 有 **40 秒兜底**自动解除，但插件必须在操作完成后主动 `BUSY 0` 并刷新数据。
遮罩期间电源键强制退出仍然可用（逃生通道）。

## 5. 消息定义 — Core → 插件

| 消息 | 时机 | 插件该做什么 |
|---|---|---|
| `INIT` | 握手完成后 | 采集初始状态，推 `CARD`/`CF` |
| `OPEN` | 用户进入详情页 | **幂等**声明全部 OBJ/list/item |
| `EV <id> <arg>` | 用户交互 | 执行动作，用 SET/BUSY 反馈 |
| `TICK` | 每秒一次（会话期间） | 轮询状态同步、刷新卡片/页面数据 |
| `CLOSE` | 用户离开详情页 | 释放页面相关临时资源（可选） |
| `EXIT` | 会话结束 | 清理并 `exit(0)` |

`EV` 的 `arg` 语义见 §4.4 交互列。`TICK` 参数由 libplugin 维护为递增秒数 `sec`。

## 6. 颜色词表（唯一允许的颜色表达）

| 词 | 语义 | 用途 |
|---|---|---|
| `n` | 主文本 | 默认 |
| `s` | 次要 | 副标题、右值 |
| `d` | 暗淡 | 不可用、未测速 `--` |
| `f` | 极淡 | 脚注 |
| `g` | 绿 | 优：延迟<200ms / 占用<30% / 电池>60% / 运行中 |
| `y` | 黄 | 良：<500 / <60% / >30% |
| `o` | 橙 | 差：<1000 / <85% / >15% |
| `r` | 红 | 危：≥1000 / ≥85% / ≤15% |

插件**只能**用这 8 个词表达颜色意图；具体色值（绿 `#3FB950` 等）与深/浅主题适配由 Core 决定。这保证全系统视觉统一，也是"其他地方不需要颜色"规则的执行机制。

## 7. 错误处理与健壮性

- Core 对无法解析的行**静默丢弃**，不回报错（保持协议简单）；插件开发期用 §8 方法自查。
- 插件崩溃/退出：Core 检测管道 EOF，标记 `alive=0`，卡片数据定格，**不影响 Core 与其他插件**。
- 插件不得在协议外假设会话时长；随时可能收到 `EXIT`（用户退出、自动锁屏、电源键）。

## 8. 调试方法

```sh
# 手写协议驱动插件（观察 Core 反应）：
{ printf 'HELLO\t2\tTest\n'; sleep 1; printf 'CARD\tON\n'; ...; } | /usr/lib/mudi/plugins/xxx

# 旁路观察插件输出（确认协议行格式）：
strace -e write -p <plugin_pid>     # 或临时把插件 stdout tee 到文件
```

## 9. 演进规则

- 新增对象类型 / 属性：向后兼容追加（旧 Core 忽略未知行、未知 k=v），`api_ver` 不变。
- 破坏性变更：`api_ver` 升至 3，Core 对低版本插件拒绝或降级处理，并在本文档记录迁移指南。
- 未来可升级为 `MSG <len> <json>` 负载；§3 生命周期与 §4 对象模型保持不变。
